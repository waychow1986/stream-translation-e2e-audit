## 阻塞项

### SPEC-SELF-001 手动流程控制行为缺少有效权威来源分类

- **严重性：** `high`
- **范围：** `self`
- **制品：** `spec.md`
- **责任 Agent：** `specification`
- **路由：** `current_stage`
- **原因类型：** `governance`
- **证据：** `spec.md` 第 12、28、31、33、54 至 57、63 至 67、79 至 84、97 至 99、119 至 174 行将“参会者发起、停止和重新发起”设为产品交互及验收义务；但批准的 `intent.md` 仅规定浏览器采集、流式处理和字幕展示，没有规定由参会者手动控制流程。追踪矩阵把 `FR-001` 归为 `direct`，把 `FR-004`、`FR-006` 归为 `closure`，却没有说明为何选择手动控制而非其他合理触发方式是消除已批准行为断点所必需的最小闭合。
- **修复建议：** 在 Specification 权限内明确该触发与终止决定；若保留手动控制，应为相关 US/FR/SC/AC/IQA 逐项提供准确的 `closure` 来源及最小闭合理由，并同步修正追踪矩阵，不能继续标为无依据的 `direct` 派生。

### SPEC-SELF-002 Azure Foundry 技术约束被泛化

- **严重性：** `high`
- **范围：** `self`
- **制品：** `spec.md`
- **责任 Agent：** `specification`
- **路由：** `current_stage`
- **原因类型：** `contradiction`
- **证据：** 批准的 `intent.md` 第 13、28、40 至 42、56 至 57 行明确将 Azure Foundry STT 服务及大模型作为客户指定约束，并以该 STT 服务确定全部自动检测语言范围。`spec.md` 第 5、7、29、45、56、104、113、130、185、218、223 至 224 行改称未具名的“客户指定语音转文本服务”“客户指定服务”或“翻译能力”，且声称后续阶段落实，未保留 Azure Foundry 与大模型这两个明确限定。
- **修复建议：** 在不引入实现设计的前提下，原样保留 `INT-006` 的 Azure Foundry STT 服务与大模型客户约束，并让语言范围、依赖、追踪和验收前置条件一致指向该获批服务。
